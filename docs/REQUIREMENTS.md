# 需求決策清單 | Requirements & Open Decisions

> 核心概念轉向後待決策的事項。每項決策定案後更新「狀態」與「結論」欄。
> 決策順序建議:D1 → D2 → D3(決定資料模型與規模),其餘可並行。

## 決策清單

### D1. 「神靈落地點」的定義與收錄範圍 ⭐ 最高優先

**問題**:落地點要標到什麼程度?

| 選項 | 內容 | 優點 | 缺點 |
|------|------|------|------|
| A | 只標精選落地點:每個神明信仰系統的開基廟/祖廟/歷史登陸點(數十至數百筆,人工策展) | 概念聚焦、資料可信、工作量可控 | 覆蓋不全,非策選廟宇不在圖上 |
| B | 全量標記:所有立案寺廟都視為該主祀神的落地點(上萬筆) | 一圖全景 | 「落地點」概念被稀釋,源流資料無法全量支撐 |
| C | 分層:全量廟宇為淺色底層 + 精選落地點為強調圖層(開基/祖廟/登陸點特殊標記) | 兩者兼得 | 工作量最大,需先完成 A 與資料匯入 |

**狀態**:✅ 已定案(2026-08-18)
**結論**:採選項 C——全量立案廟宇為淺色底圖 + 精選落地點強調圖層。

### D2. 資料來源組合

**問題**:採用哪些來源作為主檔?(候選評估見 [DATA_SOURCES.md](DATA_SOURCES.md))

- 政府開放資料(內政部寺廟資料,含主祀神欄位;統計區版本含座標)
- Wikidata 補座標與英文名
- 源流關係只能人工策展(廟史、文獻)

**狀態**:✅ 已定案並驗證(2026-08-18)——全量底圖採內政部 8203 XML:12,422 筆、含 WGS84 座標(96.0% 完整)、政府資料開放授權條款-第1版;源流自策展。驗證詳見 DATA_SOURCES.md

### D3. 源流連結的起始範圍

**問題**:第一個完整做的神明源流網絡?

- 媽祖(文獻最豐富、既有序宮廟資料最多)
- 王爺(五府千歲)、保生大帝等其他系統
- 或不分神明,先只做「個人進香之路」

**狀態**:✅ 已定案(2026-08-18)
**結論**:首批建置六大系統——**媽祖、關聖帝君、玉皇(天公廟)、觀音菩薩、地藏菩薩、阿彌陀佛**。建議實作順序由媽祖開始(文獻最豐富、既有資料最多),依次完成六系統;王爺、保生大帝等其餘系統列第二批。
**進度**:六大系統源流邊全數開展(2026-08-31)——媽祖 10 筆+觀音(安海龍山寺系)3 筆+關聖帝君 5 筆+玉皇 3 筆+地藏 1 筆+阿彌陀佛(法脈)3 筆=25 筆,均附 evidenceUrl。關聖帝君首批=開基武廟、祀典武廟、行天宮、礁溪協天廟、高雄文武聖殿;玉皇首批=沙鹿玉皇殿、開基玉皇宮、彰化元清觀;地藏首批=九華山地藏庵;阿彌陀佛首批(法脈模型,見 D10)=台中市佛教蓮社、妙通寺、台北善導寺,另收明鄭古剎台南彌陀寺為節點。新竹天公壇(神明會起家)、新莊地藏庵(厲祀起家)、鹿港地藏王廟(「四川天竺尊巖」說未獲文資普查採納)查無可定位的唐山分香文獻,僅收廟宇節點待後續考證。

### D4. 個人進香之路的儲存方式

| 選項 | 內容 | 優點 | 缺點 |
|------|------|------|------|
| A | 瀏覽器 localStorage(無帳號) | 零後端、最快上線 | 換裝置/清瀏覽器即消失 |
| B | localStorage + JSON/GPX 匯入匯出 | 無後端且可備份轉移 | 需自行管理檔案 |
| C | 後端帳號系統 | 跨裝置、可分享 | 需伺服器、隱私與個資考量,工作量劇增 |

**狀態**:✅ 已定案(2026-08-18)
**結論**:採選項 B——localStorage + JSON/GPX 匯入匯出;暫不做後端帳號,未來有跨裝置共享需求再議。

**狀態**:✅ 已定案(2026-08-18)
**結論**:降階為廟宇屬性欄位(`lodging`)保留,供規劃進香住宿參考。

### D6. 雙語政策

- 維持中英雙語(現有 i18n 架構),但全量資料的英文名稱覆蓋率是問題
- 或轉為中文為主、英文僅精選落地點

**狀態**:✅ 已定案(2026-08-18)
**結論**:中文為主;英文僅用於精選落地點。既有 i18n 架構調整為此政策服務。

### D7. 部署目標

- GitHub Pages(靜態、免費,現有架構直接可用)← 建議
- Netlify / 其他

**狀態**:✅ 已定案(2026-08-31)
**結論**:採 GitHub Pages——公開 repo 免費、純靜態架構直接部署;來源為 main 分支根目錄,每次 merge/push 自動更新線上版,網址 https://galen-chu.github.io/TAIWAN-Pilgrimage/ 。Netlify 等其他靜態托管保留為備選(D4 未來若改選 C 後端方案則另議)。

### D8. 全量資料的前端效能策略(若 D1 選 B 或 C)

- Marker clustering(Leaflet.markercluster)
- 依縣市/神明分檔、延遲載入
- 圖層開關預設只載入精選層

**狀態**:✅ 已定案(2026-08-21,v1.0 實作)
**結論**:全量層採**延遲載入**(首頁不含 moi-temples.js,首次開啟「全量廟宇」圖層才動態注入,初始載入不受 3.6MB 影響)+ **markercluster 叢集**(chunkedLoading、zoom≥15 不叢集)+ **圖層開關**(L.control.layers:精選預設開、全量預設關、源流預設開);既有神明/區域篩選同步作用於三圖層。

### D9. 神明名稱政策(2026-08-18 新增,已定案)

**原則**:原名保留,歸類不覆寫——各地對神明的不同稱呼是源流與移民脈絡的線索,資料蒐集時必須留意保留。

- 資料層保留 `mainDeityRaw`(原始主祀神名;源頭未記載者 53 筆保留為「未記載」)
- `deitySystems` 僅供系統歸類(篩選/統計/源流分組),canonical 非唯一正確稱呼
- 對照表 `data/deities.js`(11 系統)+ 未比對報告(data/raw/deity-names-report.tsv,全量共 1,950 種名稱)持續擴充
- 多主神紀錄以陣列保留全部歸類
- 源流策展記錄廟宇時,一併記錄在地稱呼

**狀態**:✅ 已定案(2026-08-18,使用者指示)

### D10. 阿彌陀佛系統的源流模型(2026-08-31 新增,已定案)

**問題**:佛教宗派傳承(師承/分院/開教)不屬民間分香模型,如何收錄?

**狀態**:✅ 已定案(2026-08-31)
**結論**:新增 relation「法脈」關係邊,用於師承與宗派傳燈(首批:印光→李炳南→台中市佛教蓮社、廣欽→傳聞→妙通寺、日治知恩院派→台北善導寺,均為官網/學術文獻可證之鏈)。非阿彌陀佛主祀之道場(承天禪寺)與海外源頭(蘇州靈巖山寺、京都知恩院)以外部節點呈現;宗派身分明確而登記主祀為釋迦牟尼佛者(台北善導寺、台南彌陀寺)以阿彌陀佛系統收錄並於 history 註明現況。齋教三派(先天/龍華/金幢)網絡另案策展。
